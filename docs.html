Developer documentation

Build against the system that actually exists.

Compflow is not a collection of simulated compliance screens. Its useful boundary is a real cloud observation → durable evidence → deterministic analysis → controlled change → fresh verification loop. This guide describes that boundary without inventing API behavior that the service does not expose.

01 · Lifecycle

A normal security/compliance operation follows this shape. Each stage has a different authority level; a later stage does not retroactively turn an earlier assumption into evidence.

1
Connect

Establish a supported cloud connection using the provider's real credentials and verification path.

2
Discover

Run a provider-backed scan and persist the resulting resources, findings and evidence.

3
Understand

Group deterministic weaknesses, establish security relationships and analyze potential exposure paths.

4
Approve

Apply the remediation policy and required role/authority before a cloud-changing operation can execute.

5
Execute

Run the authorized operation through the durable execution lifecycle with fencing and event history.

6
Verify

Collect fresh provider evidence, compare it with the baseline and re-analyze the resulting security state.

7
Prove

Only a complete, evidence-backed comparison can support a measurable security-effect claim.

02 · API surface

The following are the major service boundaries currently exposed by the application.

/api/scanStarts and manages cloud scanning operations. Organization context and credentials are enforced server-side.
/api/remediateCreates and manages remediation workflow operations subject to policy and authorization.
/api/remediation-verificationExecution, post-change verification and reanalysis lifecycle for authorized remediation.
/api/execution-graphDurable execution graph, event history and execution controls.
/api/auditorEvidence and auditor-facing verification surfaces.
/api/v1Versioned API surface for durable execution-oriented consumers.

Do not infer request or response schemas from this page. The running service and its versioned contracts are the implementation authority. When a state is unavailable or inconclusive, clients should preserve that state rather than converting it into success.

03 · Evidence

Evidence is the foundation for Compflow's security claims. A useful evidence record has provider/source lineage, timing and integrity information appropriate to the operation.

Provider observation

Direct observation from a supported cloud provider.

Fresh reanalysis

Evidence collected after a remediation for before/after comparison.

Exposure provenance

Relationships retain the evidence lineage needed to distinguish observed from inferred state.

Deterministic proof

Path/risk reduction requires complete analysis and measurable improvement; incomplete analysis stays inconclusive.

04 · AI boundary

The AI analyst is deliberately downstream of deterministic security state. It is useful for explanation and investigation, not as a replacement for the evidence system.

  • It can explain grounded findings, relationships, risk and remediation proof state.
  • It should cite the evidence and execution context supplied to it.
  • It cannot invent a relationship that the deterministic graph does not establish.
  • It cannot override provider-backed evidence or deterministic verification.
  • It cannot infer compromise merely because resources correlate.

Semantic analyst contracts such as security-analyst-v7 describe explanation behavior. They do not change the authority of evidence, graph state or remediation proof.

05 · Failure semantics

Compflow intentionally distinguishes failure from absence of evidence. A provider failure, stale evidence, incomplete graph, failed verification or unavailable persistence should remain visible to the caller.

  • Missing evidence ≠ secure.
  • API success ≠ verified cloud state.
  • Potential path ≠ confirmed compromise.
  • Verified control ≠ eliminated risk.
  • Incomplete reanalysis ≠ proven reduction.
